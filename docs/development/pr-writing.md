# swift-extension PR 작성 가이드

> PR 제목과 본문을 이 저장소 규칙에 맞게 쓰는 방법이에요. 브랜치를 만들고 커밋해서 PR을 여는 **절차와 명령**은 [Git 작업 흐름](gitflow.md)에 있어요. 이 문서는 PR에 **무엇을 어떻게 적는지**만 다뤄요.

## 이 문서를 읽으면

- 리뷰어가 diff를 열기 전에 변경 이유, 범위, 검증 결과를 파악할 수 있는 본문을 쓸 수 있어요.
- 문제 → 원인 → 해결 → 검증 순서로 설계 기록이 남는 PR을 만들 수 있어요.
- 영상, 비교 표, 기존 코드와 새 API의 대비를 언제 어떻게 넣는지 알아요.

## PR은 설계 기록이에요

이 저장소는 이슈를 만들지 않아요. 그래서 "왜 이렇게 바꿨는지"는 PR 본문에만 남아요. 몇 달 뒤 코드를 읽는 사람은 `git blame`으로 커밋을 찾고, 그 커밋이 속한 PR을 열어 배경을 확인해요. PR 본문이 diff 요약에 그치면 그때 아무것도 알 수 없어요.

그래서 이 저장소의 PR은 세 가지를 남겨요.

| 남기는 것 | 리뷰어가 얻는 것 |
| --- | --- |
| 무엇을 왜 바꿨는지 | diff를 읽는 순서와 기준 |
| 어떤 선택지가 있었고 왜 이걸 골랐는지 | 반대 의견을 낼 근거 |
| 무엇을 어떻게 검증했고 무엇을 못 했는지 | 병합 뒤 무엇을 지켜봐야 하는지 |

## 제목을 써요

제목은 `[유형] 변경 결과` 형식이고 **해요체 과거형**으로 끝내요. 유형은 브랜치 접두사·라벨과 같은 이름을 써요. 대응표는 [Git 작업 흐름](gitflow.md#7-pr을-만들고-리뷰를-요청해요)에 있어요.

| 좋은 제목 | 왜 좋은가 |
| --- | --- |
| `[feature] 탭바 뒤에서 올라오는 바텀시트를 UIKit·SwiftUI로 추가했어요` | 무엇이 새로 생겼고 어디에 적용되는지 한 줄에 있어요 |
| `[fix] 빈 스택에서 pop이 크래시하는 문제를 고쳤어요` | 증상이 드러나요. 리뷰어가 재현 조건을 상상할 수 있어요 |
| `[docs] CI 배지와 main 보호 규칙을 문서에 반영했어요` | 문서 변경도 "무엇을" 적어요 |

| 피하는 제목 | 왜 피하나 |
| --- | --- |
| `[fix] 버그 수정` | 어떤 버그인지 없어요 |
| `feat: 바텀시트 추가` | 커밋 제목 형식이에요. PR은 `[유형]`과 해요체예요 |
| `[feature] 시트 관련 여러 개선` | PR 하나에 목적이 여러 개라는 신호예요. 나눠요 |

## 본문은 템플릿 섹션을 채워요

본문은 [`.github/PULL_REQUEST_TEMPLATE.md`](../../.github/PULL_REQUEST_TEMPLATE.md)의 섹션과 순서를 그대로 써요. 안내용 HTML 주석은 지워도 돼요. 섹션마다 적을 것이 정해져 있어요.

| 섹션 | 적는 것 | 비워 두지 않아요 |
| --- | --- | --- |
| 변경 유형 | 해당하는 항목만 체크해요. 기능과 테스트와 문서가 함께 있으면 셋 다 체크해요 | — |
| 변경 내용 | 첫 문단에 **무엇을 왜** 바꿨는지 두세 문장. 그 아래에 커밋 제목별 소절 | diff 나열로 채우지 않아요 |
| 자료구조·알고리즘 영향 | 시간·공간 복잡도, 메모리 소유권, 기존 API 호환성 | 해당 없는 항목에는 `없음`이라고 적어요 |
| 검증 | 실제로 실행한 명령과 결과 숫자, 실행하지 못한 것과 이유 | 실행하지 않은 항목을 체크하지 않아요 |
| 관련 이슈 | `없음`. 이슈를 만들지 않아요 | 빈 채로 두지 않아요 |
| 추가 설명 | 설계 선택과 트레이드오프, 후속 과제, 리뷰어가 알아야 할 함정 | — |

### 변경 내용은 커밋 단위로 소절을 나눠요

커밋 제목을 굵게 적고 그 아래에 무엇을 왜 했는지 적어요. 리뷰어가 커밋 탭과 본문을 오가며 읽을 수 있어요.

```markdown
**`feat: 스크롤이 시트를 올리지 않는 scrollingExpandsSheet 옵션 추가`**

`BottomSheetBehavior.scrollingExpandsSheet`(기본 `true`)를 추가했어요. ...

| | `true` (기본) | `false` |
| --- | --- | --- |
| 낮은 단계에서 목록을 위로 끌면 | 시트가 올라가요 | 목록만 스크롤돼요 |
```

파일이 여러 개면 `파일 | 역할` 표로 정리해요. 모듈, 파일, 타입, 명령은 백틱으로 감싸요. bullet은 3~8개가 읽기 좋고, 그보다 많으면 소절을 더 나눠요.

## 개선 전과 후를 비교해요

같은 변경을 두 가지로 적어 봤어요. 개선 전은 diff를 열어야 알 수 있는 것만 있고, 개선 후는 diff를 열기 전에 리뷰어가 판단할 수 있어요.

### 개선 전

```markdown
## 변경 내용

- BottomSheetBehavior에 scrollingExpandsSheet 추가
- 컨트롤러, 모디파이어 수정
- 테스트 추가

## 검증

- [x] swift test 통과
```

### 개선 전의 문제점

1. 왜 바꿨는지 없어요. 리뷰어는 이 옵션이 어떤 문제를 푸는지 diff에서 추측해야 해요.
2. "수정"만 있고 동작이 어떻게 달라지는지 없어요. 기본값이 무엇인지, 기존 사용자에게 영향이 있는지 알 수 없어요.
3. 검증이 "통과" 한 단어예요. 어디서 몇 개를 돌렸는지, 눌러 본 것은 있는지 없어요.

### 개선 후

```markdown
## 변경 내용

시트 안 목록을 위로 끌면 시트가 먼저 올라가는 Apple 지도식 동작 대신 목록만 스크롤되길
원하는 화면이 있어서, 끄고 켤 수 있는 옵션을 추가했어요. 기본값은 UIKit 시트와 같은 `true`예요.

**`feat: 스크롤이 시트를 올리지 않는 scrollingExpandsSheet 옵션 추가`**

| | `true` (기본) | `false` |
| --- | --- | --- |
| 낮은 단계에서 목록을 위로 끌면 | 시트가 올라가요 | 목록만 스크롤돼요 |
| 목록 맨 위에서 아래로 끌면 | 시트가 내려와요 | 같아요 |

## 검증

- [x] `swift test` — macOS 30 tests, iOS 시뮬레이터 44 tests 통과
- 시뮬레이터(iPhone 16 Pro Max, iOS 26.4)에서 `tip`에서 목록을 끌어 시트는 멈추고 목록만 스크롤되는지 두 판 모두 확인했어요.
```

### 정리

- 첫 문단에 무엇을 왜 바꿨는지 두 문장으로 적었어요.
- 동작 차이를 표로 보여 줘서 기본값과 영향 범위가 드러나요.
- 검증에 환경, 숫자, 눌러 본 것을 적었어요.

## 세 가지 패턴으로 설명해요

### 문제 → 원인 → 해결 → 검증 순서로 적어요

버그나 손맛 문제를 고친 PR은 이 순서로 적어요. 증상만 적으면 리뷰어가 왜 이 diff가 답인지 알 수 없어요.

```markdown
### SwiftUI 지도 깜빡임

**증상** 시트를 끌다 손을 떼면 지도가 두 번 튀었어요. 화면을 녹화해 프레임별 차이를 재 보니
손을 뗀 프레임에 점프하고 애니메이션이 끝나는 프레임에 다시 점프했어요.

**원인** `Map`에 준 `safeAreaInset`이 애니메이션 블록 안에서 바뀌었어요. UIKit이 그리는 View는
중간값을 받지 못하고 시작과 끝에서만 반응해요.

**해결** `onOffsetChange`가 애니메이션 중에도 매 프레임 실제 위치를 주게 바꿨어요.

**검증** 같은 드래그를 다시 녹화하니 점프 프레임이 없어졌어요.
```

원인을 확인하지 못했으면 "원인은 확인 필요"라고 적고 무엇을 확인해야 하는지 남겨요. 추측을 원인처럼 쓰지 않아요.

### 기존 방식과 새 API를 나란히 보여 줘요

새 API가 지금까지 손으로 하던 코드를 대체하면, 이전 코드와 새 코드를 같은 예제로 나란히 보여 줘요. 리뷰어가 API의 가치를 바로 재요.

```swift
// 기존: 버튼 하나를 시트 윗선에 직접 제약으로 붙였어요
self.locateButton.bottomAnchor.constraint(equalTo: self.sheet.view.topAnchor, constant: -12).isActive = true

// API
self.sheet.attachDock(BottomSheetDockView(arrangedSubviews: [self.locateButton]))
```

UIKit과 SwiftUI 둘 다 바뀌면 두 블록을 모두 넣어요. 새 API의 사용법도 같은 자리에 적어요. 문서에 이미 있어도 PR에서 바로 보이는 게 리뷰에 빨라요.

### 동작 비교는 표로 적어요

옵션 `true`/`false`, 기본 시트와 커스텀 시트, A안과 B안처럼 **둘을 견주는 내용**은 문장보다 표가 빨라요. 행은 "상황", 열은 "선택지"로 두고 셀에는 결과만 적어요.

```markdown
| | 커스텀 시트 | 애플 기본 시트 |
| --- | --- | --- |
| 탭바 | 시트가 탭바 뒤로 이어지고 탭바는 눌려요 | 모달이라 탭바 위를 덮어요 |
| 위치 알림 | 끄는 동안 매 프레임 | 단계가 바뀐 뒤에만 |
```

표 안에 그림을 넣을 때는 ASCII만 써요. 한글 같은 전각 문자가 섞이면 칸이 어긋나요. 한글 설명은 그림 아래 표로 따로 둬요.

## 영상과 스크린샷을 넣어요

UI가 바뀌었으면 영상을 넣어요. 손맛, 애니메이션, 따라가는 동작은 글로 전달되지 않아요.

- UIKit과 SwiftUI 판이 있으면 두 열짜리 표에 나란히 넣어요. 표 셀에 첨부 URL만 넣으면 GitHub가 영상 플레이어로 보여 줘요.
- 영상 아래 한 줄로 어떤 순서로 무엇을 눌렀는지 적어요. 리뷰어가 무엇을 봐야 하는지 알아요.
- 길이는 10초 안팎, 크기는 수 MB 이하로 정리해요. 조작 사이의 정지 구간은 잘라 내요.
- 시뮬레이터는 `xcrun simctl io <udid> recordVideo <경로>`로 녹화해요.
- 첨부는 GitHub 편집기에 파일을 끌어 놓아야 돼요. `gh`나 API로는 올릴 수 없어요. 아직 올리지 못했으면 표 셀에 `(영상은 따로 첨부해요)`라고 적어 두고 비워 두지 않아요.

```markdown
| UIKit `BottomSheetController` | SwiftUI `bottomSheet(detent:)` |
| --- | --- |
| https://github.com/user-attachments/assets/... | https://github.com/user-attachments/assets/... |

`tip`에서 목록 스크롤(시트는 그대로) → 손잡이로 `half` → `full` 버튼 → `hidden` → `tip`.
```

## 검증은 사실만 적어요

검증 섹션은 리뷰어가 가장 먼저 믿어야 하는 부분이에요. 확인한 것만, 확인한 만큼만 적어요.

| 이렇게 | 이렇게 하지 않아요 |
| --- | --- |
| `swift test` macOS 34 tests, iOS 시뮬레이터 56 tests 통과 | 테스트 통과 |
| Release 구성에서 10만 개 요소로 측정했고 중앙값이 12% 줄었어요 | 성능이 크게 개선됐어요 |
| 실기기 검증은 하지 못했어요. 시뮬레이터 iPhone 16 Pro Max에서만 확인했어요 | (실기기 항목을 체크) |
| 원인은 `확인 필요`예요. `BottomSheetController.swift`의 `animate(to:)` 타이밍을 봐야 해요 | 아마 타이밍 문제일 거예요 |

- 시뮬레이터에서 눌러 본 것은 `확인 | 결과` 표로 적어요. 기기와 OS 버전을 표 제목에 넣어요.
- 실행하지 못한 검증은 이유와 함께 적어요. 이유가 환경 문제(결제, 권한, 기기 없음)이면 그것도 적어요.
- diff를 그대로 나열하지 않아요. 자동 리뷰 도구의 요약을 사람이 쓴 것처럼 붙이지 않아요.
- 비밀값, 토큰, 팀 ID, 인증 파일 내용을 본문에 쓰지 않아요.
- AI 공동 작성자 표기, 생성 문구, 세션 링크를 넣지 않아요. [AI 작성 표기 규칙](ai-attribution.md)을 따라요.

## 문체를 맞춰요

- 본문은 **해요체**로 통일해요. 표 안 문장도 같아요. 커밋 제목만 `feat: RingBuffer 추가`처럼 개조식이에요.
- 한 문장에 하나만 적어요. "~하고 ~해서 ~했어요"가 길어지면 나눠요.
- 주체를 분명히 해요. "수정되었어요"보다 "`offset(for:)`가 같은 이름의 단계를 먼저 찾도록 바꿨어요"가 리뷰에 도움이 돼요.
- 모듈, 파일, 타입, 메서드, 명령, 경로는 백틱으로 감싸요.
- 다듬을 때는 [한국어 윤문 원칙](korean-editing.md)을 따라요. 의미와 사실을 바꾸지 않고 번역투만 고쳐요.

## 커밋이 늘어나면 본문도 갱신해요

PR을 연 뒤에 커밋이 더 붙으면 본문도 같은 시점에 갱신해요. 검증 숫자, 소절, 후속 과제가 오래된 채로 남으면 리뷰어가 diff와 본문을 대조할 수 없어요.

```bash
gh pr view <번호> --json body -q .body > pr-body.md
# pr-body.md를 고친 뒤
gh pr edit <번호> --body-file pr-body.md
```

새 커밋이 앞선 커밋의 문제를 고쳤으면 본문에 그 사실도 적어요. "첫 구현에서 시뮬레이터 테스트 3개가 실패해서 `offset(for:)`를 고쳤어요"처럼요. 리뷰어가 같은 함정을 다시 밟지 않아요.

## 쌓인 PR은 base를 본문에 적어요

아직 병합되지 않은 기능 브랜치 위에 새 PR을 열 때는(stacked PR, 쌓인 PR) 첫 문단에 base(대상) 브랜치와 이유를 적어요. 리뷰어가 diff 범위를 바로 알고 병합 순서를 정할 수 있어요.

```markdown
#7 위에 쌓인 PR이라 base가 `feature/bottom-sheet`예요. #7이 병합되면 `main`으로 바꿔요.
```

병합 순서를 잘못 잡으면 위 PR의 커밋이 `main`에 들어가지 않아요. 순서와 base를 바꾸는 명령은 [Git 작업 흐름](gitflow.md#8-병합-후-브랜치를-정리해요)에 있어요.

## 게시 전에 확인해요

- [ ] 제목이 `[유형] 변경 결과` 형식이고 해요체 과거형이에요.
- [ ] 첫 문단에 무엇을 왜 바꿨는지 있어요.
