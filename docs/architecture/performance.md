# swift-extension 성능 기준

> 이 라이브러리는 "표준 라이브러리보다 빠르거나, 표준 라이브러리에 없는" 구현을 목표로 해요. 그래서 성능 주장은 측정 결과로만 해요. 측정하지 않은 개선은 개선이라고 적지 않아요.

## 만들기 전에 확인해요

새 자료구조를 만들기 전에 아래를 확인해요.

1. 표준 라이브러리의 `Array`, `Set`, `Dictionary`, `ContiguousArray`로 충분한가요?
2. [swift-collections](https://github.com/apple/swift-collections)의 `Deque`, `OrderedSet`, `Heap` 등으로 충분한가요?
3. 충분하지 않다면, 어떤 연산이 어떤 입력 크기에서 문제가 되나요?

3번에 답할 수 있을 때만 새 구현을 시작해요. 답을 PR 본문의 `변경 내용`에 적어요.

## 값 의미론과 복사 최소화

자료구조는 값 타입으로 만들되, 요소 저장소를 복사하는 비용은 쓰기 시점까지 미뤄요(Copy-on-Write).

- 저장소를 `Array`나 `ContiguousArray`에 위임하면 CoW는 표준 라이브러리가 처리해요. 특별한 이유가 없으면 이 방법을 먼저 선택해요.
- 직접 버퍼를 관리할 때는 `isKnownUniquelyReferenced(_:)`로 고유 참조를 확인하고, 공유 중일 때만 복사해요.

```swift
// 직접 버퍼를 관리할 때의 CoW 기본 형태
private mutating func makeUniqueIfNeeded() {
    guard !isKnownUniquelyReferenced(&self.buffer) else { return }

    self.buffer = self.buffer.copy()
}
```

- `mutating` 메서드 안에서 저장 프로퍼티를 여러 번 읽고 쓰면 불필요한 복사나 유지 카운트 연산이 생길 수 있어요. 지역 변수로 한 번만 꺼내 쓰는 형태를 검토해요.
- 값 의미론이 깨지면 성능보다 먼저 정확성 문제예요. 복사본을 수정했을 때 원본이 바뀌지 않는지 테스트로 확인해요.

## 할당과 버퍼

- 최종 크기를 알면 `reserveCapacity(_:)`로 재할당을 줄여요.
- 요소가 클래스 참조를 담지 않고 브리징이 필요 없다면 `Array` 대신 `ContiguousArray`를 검토해요.
- 힙 버퍼를 직접 소유해야 하면 `ManagedBuffer`나 `UnsafeMutablePointer` 계열을 쓰고, 해제 책임을 한 곳에 모아요.
- 컬렉션을 순회하며 새 컬렉션을 만들 때는 중간 배열을 여러 번 만들지 않는지 확인해요.
- 요소 타입이 제네릭일 때는 크기와 정렬을 가정하지 않아요.

## 인라인화와 모듈 경계

모듈 밖에서 호출되는 작은 연산은 인라인화되지 않으면 호출 비용이 그대로 남아요.

- 한 줄짜리 접근자나 짧은 연산 중 성능이 중요한 것에는 `@inlinable`을 검토해요.
- `@inlinable` 함수가 참조하는 내부 선언에는 `@usableFromInline`이 필요해요. 두 속성은 내부 구현을 쓰는 쪽 모듈에 노출하므로, 나중에 바꾸기 어려워져요. 측정으로 이득을 확인한 곳에만 붙여요.
- 상속이 필요 없는 클래스에는 `final`을 붙여 동적 디스패치를 줄여요.
- 프로토콜을 통한 호출이 병목이면 제네릭 제약(`some`, `where`)으로 정적 디스패치가 되게 바꾸는 것을 검토해요.

## Unsafe API 사용 기준

`Unsafe...` 계열은 정말 필요할 때만 쓰고, 다음을 지켜요.

- 안전한 구현을 먼저 만들고 테스트를 통과시킨 뒤에 바꿔요.
- 경계 검사를 `assert`나 `precondition`으로 남겨요. 디버그 빌드에서 잘못된 인덱스가 잡히게 해요.
- 포인터의 유효 범위를 벗어난 곳으로 값을 내보내지 않아요.
- `@unchecked Sendable`, 수동 메모리 해제처럼 컴파일러 검사를 우회하는 코드에는 그 이유를 주석으로 적어요.
- Unsafe 코드를 추가한 PR에는 Address Sanitizer 결과를 함께 적어요.

## 측정 방법

디버그 빌드의 숫자는 성능 근거로 쓰지 않아요. 최적화가 꺼져 있어 실제 사용 환경과 다르게 나와요.

```bash
# 릴리즈 빌드로 컴파일 확인
swift build -c release

# 릴리즈 구성으로 테스트 실행
swift test -c release
```

측정할 때는 다음을 함께 기록해요.

| 기록할 항목 | 예시 |
| --- | --- |
| 측정 환경 | Apple M 시리즈, macOS 버전, Swift 버전 |
| 빌드 구성 | `-c release` |
| 입력 크기 | 요소 10만 개, 랜덤 순서 |
| 비교 대상 | 표준 라이브러리 `Array` 기반 구현 |
| 반복 횟수와 결과 | 10회 실행, 중앙값 |

- 벤치마크 하니스는 아직 저장소에 없어요. `확인 필요`: 반복 측정이 필요해지면 `swift-collections-benchmark` 도입 여부를 먼저 정해요.
- 한 번의 실행 시간 차이는 노이즈일 수 있어요. 여러 번 실행한 값의 중앙값으로 비교해요.
- 복잡도가 좋아졌다고 항상 빨라지지는 않아요. 작은 입력에서 느려지지 않았는지도 확인해요.

## 성능 변경 PR 체크리스트

- [ ] 바꾸기 전과 후의 시간·공간 복잡도를 적었어요.
- [ ] Release 구성에서 측정했고, 환경과 입력 크기를 적었어요.
- [ ] 값 의미론과 기존 동작이 유지되는지 테스트로 확인했어요.
- [ ] 작은 입력에서 느려지지 않았는지 확인했어요.
- [ ] Unsafe 코드나 동시성 관련 변경이 있으면 Sanitizer 결과를 적었어요.
- [ ] `@inlinable`·`@usableFromInline`을 추가했다면 호환성 영향을 적었어요.
